# Локальный запуск Istighfar

Локальная машина и прод не связаны. Команды из этого файла поднимают PostgreSQL в Docker, API на порту 3000 и интерфейс на порту 5173. На сервер это не попадает.

Прод обновляется только пушем в `main`: GitHub Actions заходит на сервер и делает `git pull origin main`. Пока пуша нет, можно коммитить локально сколько угодно.

Все команды выполняются из корня репозитория, в PowerShell.

## Что должно быть установлено

- [Bun](https://bun.sh) 1.4 или новее.
- [Docker Desktop](https://www.docker.com/products/docker-desktop/). Мало установить его: перед работой приложение Docker должно быть запущено, иконка кита в трее не должна крутиться бесконечно. Пока движок Docker не запущен, `bun run db:up` не поднимет базу.

## Первый запуск

Один раз на этой машине:

```powershell
bun install
Copy-Item .env.example .env
Copy-Item .env.example apps\api\.env
bun run db:up
bun run db:generate
bun run db:deploy
```

Что делает каждый шаг:

1. `bun install` ставит зависимости монорепозитория.
2. Два `.env` копируются из примера. Корневой файл читает Vite, `apps\api\.env` читает API. Оба файла в Git не попадают. Секрет `JWT_ACCESS_SECRET` в примере уже длиннее 32 символов, для локальной машины его можно не менять.
3. `db:up` поднимает контейнер `istighfar-postgres`: PostgreSQL 16, порт `5432`, пользователь `istighfar`, пароль `istighfar`, база `istighfar`. Рядом создаётся пустая `istighfar_test` для интеграционных тестов.
4. `db:generate` собирает клиент Prisma.
5. `db:deploy` создаёт таблицы в локальной базе. Без этого шага API стартует, а вход падает с 500.

Данные лежат в томе Docker `istighfar_pg`. `bun run db:down` останавливает контейнер и том не удаляет: пользователи и отчёты остаются до следующего `db:up`.

## Каждый следующий запуск

1. Запустите Docker Desktop и дождитесь, пока движок поднимется.
2. Поднимите базу, если контейнер ещё не работает:

```powershell
bun run db:up
```

3. В двух отдельных терминалах:

```powershell
bun run dev:api
```

```powershell
bun run dev:web
```

`bun dev:api` и `bun dev:web` делают то же самое: Bun сам подставляет `run`.

API перезапускается при правках в `apps\api`. Vite обновляет страницу при правках в `apps\web`. Процессы перезапускать из‑за обычных правок кода не нужно. Перезапуск Vite нужен только после изменения корневого `.env`.

## Куда открывать браузер

Смотрите `VITE_API_URL` в корневом `.env` и открывайте интерфейс на том же хосте.

| `VITE_API_URL` | Страница |
| --- | --- |
| `http://localhost:3000` | http://localhost:5173 |
| `http://127.0.0.1:3000` | http://127.0.0.1:5173 |

`localhost` и `127.0.0.1` для браузера — разные сайты. Если страница на одном, а API на другом, вход может ответить успешно, но cookie сессии браузер не сохранит, и следующее обновление страницы снова покажет экран входа.

В `.env.example` адрес API — `http://localhost:3000`, а `CORS_ORIGINS` — `http://localhost:5173`. Если локально стоит `http://127.0.0.1:3000`, откройте http://127.0.0.1:5173. После смены `VITE_API_URL` остановите `bun run dev:web` и запустите его снова.

Проверка, что API жив: http://localhost:3000/health или http://127.0.0.1:3000/health, в зависимости от того, какой хост указан в `VITE_API_URL`. Ответ `{"status":"ok"}` значит только то, что процесс Nest запущен. Базу этот адрес не проверяет.

## Вход и регистрация

Локальная база пустая и не связана с продом. Email и пароль с продакшена здесь не существуют, пока вы не зарегистрируете эту учётку заново на локальном API.

На странице входа перейдите к регистрации и создайте пользователя. После этого этим же email можно входить локально. Семью тоже нужно создать заново: на проде она остаётся своей.

Если регистрация отвечает текстом «Регистрация временно отключена», в [apps/api/src/auth/auth.controller.ts](apps/api/src/auth/auth.controller.ts) включён метод `register`, который сразу выбрасывает `ForbiddenException`. Для локальной работы нужен метод, который вызывает `this.auth.register(body)`.

## Остановка

В терминалах API и Vite нажмите `Ctrl+C`.

Базу можно оставить запущенной. Если она больше не нужна:

```powershell
bun run db:down
```

## Если вход отвечает 500

`POST /auth/login` с кодом 500 почти всегда значит, что Prisma не смогла прочитать таблицу пользователей. Неверный пароль даёт 401 и текст «Неверный email или пароль», а не 500.

Проверьте по порядку:

1. Docker Desktop запущен.
2. Контейнер поднят: `bun run db:up`.
3. Порт слушается. В PowerShell `Test-NetConnection 127.0.0.1 -Port 5432` должен показать `TcpTestSucceeded : True`.
4. Миграции применены: `bun run db:deploy`.

`/health` при этом может оставаться зелёным: он не ходит в PostgreSQL. Ошибка видна в терминале, где запущен `bun run dev:api`, в стеке `UsersService.findAuthByEmail`.

## Схема базы во время разработки

Новую миграцию после изменения `apps\api\prisma\schema.prisma` создаёт:

```powershell
bun run db:migrate
```

`db:deploy` только применяет уже существующие миграции. Клиент Prisma после изменения схемы обновляет `bun run db:generate`.

Команду `npx prisma` без версии не используйте: она может поставить другую линию Prisma. Нужны скрипты `bun run db:generate`, `bun run db:migrate` и `bun run db:deploy`.
